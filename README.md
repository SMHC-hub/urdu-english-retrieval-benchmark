# Urdu-English Code-Switching Retrieval Benchmark
### How much do dense retrieval models degrade when queries switch between Urdu and English?

## Overview

Code-switching — the natural alternation between two languages in a single utterance — is the default communication mode for hundreds of millions of Pakistani and South Asian users. Yet modern retrieval systems are almost exclusively benchmarked on clean, monolingual English queries.

**This benchmark answers:**
> *How badly do state-of-the-art dense retrieval models degrade when users type queries in code-switched Urdu-English — both in native Urdu script (`ur_en`) and Roman Urdu (`roman`) — against English corpora?*

## Key Findings

### Performance Degradation vs. English Baseline (nDCG@10)

| Model | Dataset | EN Baseline | ur_en | roman | Drop (ur_en) |
|-------|---------|-------------|-------|-------|-------------|
| `e5-base-v2` | SciFactact | 0.710 | 0.650 | 0.621 | **−8.5%** |
| `bge-base-en-v1.5` | SciFactact | 0.738 | 0.596 | 0.625 | **−19.2%** |
| `multilingual-e5-base` | SciFactact | 0.689 | 0.662 | 0.614 | **−3.8%** |
| `bge-m3` | SciFactact | 0.644 | 0.642 | 0.558 | **−0.2%** |
| `e5-base-v2` | NFCorpus | 0.353 | 0.326 | 0.329 | **−18.1%** |
| `bge-base-en-v1.5` | NFCorpus | 0.368 | 0.335 | 0.339 | **−20.6%** |
| `multilingual-e5-base` | NFCorpus | 0.311 | 0.301 | 0.292 | **−8.3%** |
| `bge-m3` | NFCorpus | 0.314 | 0.312 | 0.298 | **−2.0%** |

### Embedding Space Divergence (Cosine Similarity: EN vs CS)

| Model | cos(EN, ur_en) | cos(EN, roman) | drift_UR | drift_ROM |
|-------|---------------|----------------|----------|-----------|
| `e5-base-v2` | 0.9066 | 0.9042 | 0.093 | 0.096 |
| `bge-base-en-v1.5` | 0.8083 | 0.8199 | **0.192** | **0.180** |
| `multilingual-e5-base` | 0.9433 | 0.9156 | 0.057 | 0.084 |
| `bge-m3` | 0.9323 | 0.7937 | 0.068 | **0.206** |

> [!NOTE]
> **Methodology Note on % Drop Computation:**
> - **SciFact ($n=300$):** All 300 test queries were code-switched; baseline and degraded evaluations are directly comparable across the full corpus.
> - **NFCorpus ($n=136$ paired subset / 323 total):** Code-switching was generated for a focused paired subset of 136 queries. The **Drop (ur_en)** column reflects the true paired degradation computed strictly on the $n=136$ code-switched queries (`e5-base-v2` drops from $0.3562 	o 0.2916$, exactly **-18.1%**). In contrast, the `EN Baseline` (0.353) and `ur_en` (0.326) columns report corpus-wide macro nDCG@10 across all 323 queries, where the 187 unperturbed English queries dampen the aggregate corpus drop to -7.6%.

**Key takeaway:** Monolingual English-centric models (`bge-base-en-v1.5`) suffer the most — up to **20.6% nDCG@10 drop** on NFCorpus. Multilingual models (`multilingual-e5-base`, `bge-m3`) are substantially more robust to code-switching in the native Urdu script condition, though `bge-m3` unexpectedly degrades on Roman Urdu due to poor Roman script coverage.

## Pipeline

```
┌──────────────────────────────────────────────────────────────────┐
│  01_get_data        Download SciFactact + NFCorpus from BEIR hub       │
│  02_baseline        Run 4 models × 2 datasets on English queries │
│  03_generate        LLaMA 3.3-70B (Groq) → code-switched JSONL  │
│  04_verify          Spot-check 50 samples, save to Excel         │
│  05_fix             Re-generate low-quality / failed queries     │
│  06_degradation     Run all models on ur_en + roman conditions   │
│  07_divergence      Embedding PCA + cosine drift analysis        │
│  08_figures         Produce publication-ready figures            │
└──────────────────────────────────────────────────────────────────┘
```

### Code-Switching Conditions

| Condition | Description | Example |
|-----------|-------------|---------|
| **`ur_en`** | Native Urdu script + English technical terms | `ذیابیطس کی causes کیا ہیں؟` |
| **`roman`** | Roman Urdu (Latin letters) + English | `diabetes ki wajahaat kya hain?` |

Queries were generated by **LLaMA 3.3-70b-versatile** (via Groq API) prompted to behave as a native Urdu-speaking Pakistani user. 300 SciFactact + 136 NFCorpus queries were generated per condition.

## Setup & Reproduction

### Prerequisites
- Python 3.10+
- Groq API key (free at [console.groq.com](https://console.groq.com)) — only needed for `03_generate.ipynb`
- GPU recommended for steps 02, 06, 07 (CPU works but is slow)

### 1. Clone

```bash
git clone https://github.com/SMHC-hub/urdu-english-retrieval-benchmark.git
cd urdu-english-retrieval-benchmark
```

### 2. Create Virtual Environment

```bash
python -m venv venv
# Windows:
venv\Scripts\activate
# macOS/Linux:
source venv/bin/activate
```

### 3. Install Dependencies

```bash
# Install PyTorch (GPU)
pip install torch --index-url https://download.pytorch.org/whl/cu126

# Install all other dependencies
pip install -r requirements.txt
```

### 4. Configure API Keys

```bash
cp .env.example .env
# Edit .env and add your GROQ_API_KEY
```

### 5. Verify Setup

```bash
python 00_smoke_test.py
# Expected output:
# Device: cuda
# Embedding shape: (1, 768)
# Smoke test passed.
```

### 6. Run the Pipeline (in order)

```bash
jupyter notebook
```

Run notebooks `01` → `08` in sequence. Each notebook saves its outputs to `results/` or `queries/` — later notebooks read those files, so order matters.

> **Shortcut:** If you only want to reproduce the analysis (skip data download + LLM generation), the `queries/` and `results/` CSVs are already committed. Start from `06_degradation.ipynb`.

## Reproducibility Notes

- All retrieval uses **cosine similarity** (`score_function="cos_sim"`) via BEIR's `DenseRetrievalExactSearch`
- Batch size: 32 for retrieval, 64 for embedding divergence
- LLM generation used `llama-3.3-70b-versatile` at temperature 0 for determinism
- `verification_sample.xlsx` contains a 50-query human spot-check of generation quality
